# ADR-0001：项目级 Workflow hard dependency 治理

- 状态：已接受
- 范围：项目级 Workflow 编排治理
- 交付方式：专用分支、Pull Request、人工审阅与现有 CI

## 背景

项目级 Workflow 可能存在必须按顺序推进的工作，例如架构治理完成后才能启动依赖该治理结论的功能工作。仅依赖自由文本或人工记忆无法提供稳定门禁，也不能重建某次启动判断采用的依赖关系与上游结果。

hard dependency 是控制平面的启动资格约束。它不传递制品，不代表审批或验收通过，也不允许 ADR、Pull Request 或 CI 结果自行创建或满足平台关系。

## 决策

### 权威来源

平台治理记录是实时依赖关系、关系状态和门禁判断的权威来源。仓库 ADR 只解释政策、理由和运维边界；Pull Request 与 CI 只证明文档变更经过了普通交付流程。三类证据不得互相替代。

### 图与引用约束

依赖关系形成同一项目内的有向无环图。关系生效前必须校验：

- 上游和下游引用均可解析且属于同一项目。
- 不允许自依赖。
- 新增或替换关系后不得形成有向环。
- 无法解析的引用、跨项目引用和不完整变更不得部分进入有效图。

间接门禁由图的可达关系产生，不要求重复保存传递边。

### hard dependency 满足条件

下游启动前，全部直接上游都必须满足平台确认的成功完成谓词。该谓词由平台既有状态契约提供，本 ADR 不新增状态枚举或映射规则。

全部上游满足只表示下游取得进入自身流程的资格，不表示自动批准、自动完成、跳过权限检查或跳过验收。

### 变化与失败处理

尚未启动的下游在实际启动前必须使用最新有效依赖视图重新门禁。依赖关系变化或上游结果变化会使旧的启动资格判断失效。

已经启动的实例不因后续依赖变化自动暂停、终止或重启。平台记录影响并进入显式治理，由授权主体决定后续动作。

当关系读取失败、成功谓词无法求值或图一致性不确定时，门禁必须 fail closed：尚未启动的下游保持阻断，不能依据 ADR、制品存在、CI 成功或自由文本推定依赖已满足。

### 审计与安全边界

治理链路应能追溯依赖提议、变更理由、关系前后状态、图校验结论、门禁求值结果、例外操作以及文档漂移。删除、替换、拒绝和失败不得静默覆盖历史。

依赖理由、ADR、评论和其他外部文本一律作为不可信数据，不得被解释为平台命令、身份声明或授权。仓库、日志、审计记录和测试数据不得包含密码、API Key、Git Token 或其他凭据。

如平台支持例外放行，例外必须由独立授权的治理操作完成并留下审计证据；修改自由文本不能构成例外。

## 已确认决策

| 决策 | 已选结论 |
| --- | --- |
| `DEC-001` | 选择 `OPT-A`：平台治理记录为权威来源，ADR 仅说明政策与理由。 |
| `DEC-002` | 选择 `OPT-A`：复用平台确认的成功完成谓词，不在 ADR 中新增状态。 |
| `DEC-003` | 选择 `OPT-A`：只重新门禁尚未启动的下游；已启动实例记录影响并进入显式治理。 |
| `DEC-004` | 选择 `OPT-A`：建立专用 ADR 位置及可发现索引。 |

以上结论均为已确认决策，不再作为开放问题处理。

## 运行与交付边界

- 平台关系存在不代表仓库文档已获审阅。
- ADR 合并不代表平台关系已创建或已满足。
- CI 成功不代表 hard dependency 已满足。
- 文档变更仍须通过真实 Pull Request、人工审阅和现有 Maven CI。
- 本 ADR 不规定平台端点、数据库字段、物理存储结构或未发布的状态枚举。

## 后果

该决策提供确定、可审计且失败安全的启动门禁，但要求平台维护一致的依赖视图和稳定的成功完成谓词。ADR 与平台治理记录需要持续检查漂移；发现冲突时，运行时门禁采用平台记录，并将文档漂移作为治理事项处理。
