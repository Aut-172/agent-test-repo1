# 设备维护工单与 SLA 告警服务——软件需求规格说明书

文档版本：1.0
状态：测试基线候选
适用项目：Maintenance SLA Service

## 1. 文档目的

本文定义制造企业设备维护工单与 SLA 告警服务的业务范围、参与者、功能需求、质量属性、数据约束、验收标准和可追溯规则。本文是产品、架构、开发、测试和运维共同使用的权威需求输入。

## 2. 背景与问题

生产现场目前通过电话、即时消息和表格分散记录设备故障。工单优先级口径不一致，受理与解决时限缺少自动计算，状态可以被任意修改，导致停机时间、责任边界和审计数据不可靠。

系统需要提供一个最小但严格的工单核心服务，使上层门户、移动端或集成系统能够用一致方式创建和推进维护工单，并可判断工单是否违反响应或解决 SLA。

## 3. 目标

1. 所有维护请求获得唯一工单编号和可追溯创建时间。
2. 优先级决定响应与解决时限，计算规则稳定且可测试。
3. 状态变化遵循明确状态机，非法跳转必须被拒绝。
4. 关闭工单前必须完成解决动作并记录解决摘要。
5. 系统能够在任意时间点判断响应 SLA 与解决 SLA 是否逾期。
6. 核心领域逻辑与 Web、数据库、消息中间件解耦。

## 4. 非目标

- 不实现完整资产台账、备件库存、采购和财务结算。
- 不实现排班优化、自动派工和路线规划。
- 不实现短信、邮件或即时通信供应商适配器。
- 不在当前版本实现多租户计费。
- 不允许 Agent 或外部集成自动关闭工单。

## 5. 参与者

| 参与者 | 职责 |
| --- | --- |
| 报修人 | 提交故障信息，查看状态 |
| 维修协调员 | 受理、分派、取消重复或无效工单 |
| 维修工程师 | 开始处理、记录解决结果 |
| 维修主管 | 审核关闭、查看 SLA 和审计信息 |
| 外部系统 | 通过 API 创建或查询工单 |

## 6. 术语

- **响应 SLA**：从创建到首次受理允许的最长时间。
- **解决 SLA**：从创建到标记解决允许的最长时间。
- **逾期**：当前时间超过对应截止时间且目标动作尚未完成。
- **解决**：维修工程师完成技术处理，但工单尚待主管确认关闭。
- **关闭**：主管确认结果完整，工单生命周期结束。

## 7. 工单优先级

| 优先级 | 场景 | 响应时限 | 解决时限 |
| --- | --- | ---: | ---: |
| CRITICAL | 产线停机、安全风险、核心设备不可用 | 15 分钟 | 4 小时 |
| HIGH | 产能显著下降、关键功能退化 | 30 分钟 | 8 小时 |
| MEDIUM | 局部异常、有临时绕行方案 | 4 小时 | 24 小时 |
| LOW | 预防性维护、非紧急改进 | 8 小时 | 72 小时 |

所有时限按自然时间计算。时区由调用方传入的绝对时间决定，领域层只处理 `Instant`。

## 8. 状态模型

状态集合：

- `OPEN`：已创建，尚未受理。
- `ACKNOWLEDGED`：协调员已受理。
- `IN_PROGRESS`：维修工程师正在处理。
- `RESOLVED`：技术处理完成，等待关闭。
- `CLOSED`：主管已关闭。
- `CANCELLED`：重复、误报或不再需要处理。

允许的状态变化：

1. `OPEN -> ACKNOWLEDGED`
2. `ACKNOWLEDGED -> IN_PROGRESS`
3. `IN_PROGRESS -> RESOLVED`
4. `RESOLVED -> CLOSED`
5. `OPEN -> CANCELLED`
6. `ACKNOWLEDGED -> CANCELLED`

其他变化一律拒绝。终态 `CLOSED` 和 `CANCELLED` 不允许再变化。

## 9. 功能需求

### FR-001 创建工单

系统必须接收标题、描述、设备编号、优先级、报修人和创建时间。标题、描述、设备编号和报修人不能为空。创建后状态必须为 `OPEN`，并同时计算响应和解决截止时间。

验收标准：

- 输入有效时返回具有唯一 ID 的工单。
- `acknowledgementDeadline` 和 `resolutionDeadline` 与优先级规则一致。
- 空白标题、设备编号或报修人被拒绝。

### FR-002 受理工单

只有 `OPEN` 工单可以受理。系统记录受理时间和受理人。受理时间不得早于创建时间。重复受理、解决或取消后的受理必须被拒绝。

### FR-003 开始处理

只有 `ACKNOWLEDGED` 工单可以开始处理。系统记录开始时间和工程师。

### FR-004 标记解决

只有 `IN_PROGRESS` 工单可以解决。解决摘要必须为非空文本，解决时间不得早于创建时间。

### FR-005 关闭工单

只有 `RESOLVED` 工单可以关闭。关闭动作记录关闭时间。关闭时间不得早于解决时间。关闭动作必须由上层权限系统限制为维修主管。

### FR-006 取消工单

只有 `OPEN` 或 `ACKNOWLEDGED` 工单可以取消。取消原因必须为非空文本。已经开始处理的工单不得取消，应通过解决流程结束。

### FR-007 响应 SLA 判定

当工单尚未受理且检查时间晚于响应截止时间时，响应 SLA 为逾期。已经受理的工单根据实际受理时间与截止时间判断是否逾期。

### FR-008 解决 SLA 判定

当工单尚未解决且检查时间晚于解决截止时间时，解决 SLA 为逾期。已经解决的工单根据实际解决时间与截止时间判断是否逾期。

### FR-009 审计信息

领域对象必须保留创建、受理、开始处理、解决、关闭或取消的关键时间与操作者字段。领域层不得静默覆盖已记录的历史动作。

### FR-010 查询

后续 API 层应支持按 ID 查询，以及按设备、状态、优先级和创建时间区间分页查询。当前领域核心不规定具体数据库实现。

## 10. 数据需求

工单至少包含 ID、标题、描述、设备 ID、优先级、状态、报修人、创建时间、两个 SLA 截止时间，以及受理、处理、解决、关闭或取消的时间和操作者信息。

## 11. 非功能需求

- **正确性**：所有状态变化和 SLA 计算必须由固定时间单元测试覆盖。
- **可审计性**：非法动作抛出明确异常，不允许静默忽略。
- **可维护性**：领域模型不得依赖 Web 框架、ORM 或云 SDK。
- **性能**：单个领域动作不执行网络或磁盘 I/O；未来查询 API 在 10 万工单规模下 P95 低于 300 ms。
- **安全**：认证授权在 API 层实施；所有外部文本均视为不可信数据。
- **兼容性**：Java 17、Maven、Linux CI。

## 12. 业务规则

- BR-001：解决截止时间必须晚于响应截止时间。
- BR-002：所有动作时间不得早于创建时间。
- BR-003：关闭时间不得早于解决时间。
- BR-004：同一业务动作只允许成功一次。
- BR-005：终态不可逆。
- BR-006：恰好等于截止时间不算逾期，严格晚于才算逾期。
- BR-007：取消原因和解决摘要去除首尾空白后仍须非空。

## 13. 可追溯验收场景

- AC-001：创建 CRITICAL 工单，响应截止为 15 分钟，解决截止为 4 小时。
- AC-002：创建 LOW 工单，响应截止为 8 小时，解决截止为 72 小时。
- AC-003：OPEN 工单受理成功，重复受理失败。
- AC-004：ACKNOWLEDGED 工单开始处理成功。
- AC-005：IN_PROGRESS 工单以非空摘要解决成功。
- AC-006：RESOLVED 工单关闭成功。
- AC-007：OPEN 工单可取消，IN_PROGRESS 工单不可取消。
- AC-008：检查时间等于截止时间时不逾期，晚 1 纳秒时逾期。
- AC-009：非法跨级状态变化被拒绝。
- AC-010：任何终态的后续动作被拒绝。

## 14. 发布门禁

1. `mvn verify` 成功。
2. 需求变更同步更新 SRS、架构和测试计划。
3. 状态机或 SLA 规则变更包含回归测试。
4. 仓库、日志和测试数据不得包含密码、API Key 或 Git Token。
5. 所有变更通过人工代码审阅。
